## Overview

LNKD's design prioritizes **speed**, **simplicity**, and **scientific accuracy**. This document explains key architectural decisions and their tradeoffs.

---

## Decision 1: KD-Tree Spatial Indexing

**Choice**: Use scikit-learn's KDTree for neighbor queries

**Alternatives considered**:
1. Brute-force O(n²) distance calculations
2. Grid-based spatial hashing
3. Octree or R-tree structures

### Why KD-Tree?

<Tabs>
  <Tab title="Performance">
    **Brute force**: O(n²) = 780² = 608,400 calculations
    **KD-tree**: O(n log n) ≈ 780 × log₂(780) ≈ 7,500 operations

    **Significant computational advantage** from reduced operation count
  </Tab>

  <Tab title="Simplicity">
    ```python
    # KD-tree (3 lines)
    tree = KDTree(coords)
    indices, distances = tree.query_radius(coords, r=10.0)

    # vs. brute force (nested loop)
    for i, atom1 in enumerate(atoms):
        for j, atom2 in enumerate(atoms):
            if i != j:
                dist = np.linalg.norm(atom1.coords - atom2.coords)
                if dist < 10.0:
                    pairs.append((i, j, dist))
    ```

    **KD-tree abstracts complexity**, delegated to sklearn (well-tested)
  </Tab>

  <Tab title="3D Optimization">
    KD-trees excel in **low dimensions** (3D coordinates)
    - Binary space partitioning efficient for d ≤ 10
    - Molecular structures inherently 3D
    - Perfect fit for LNKD's use case
  </Tab>
</Tabs>

**Tradeoff**: Requires sklearn dependency (acceptable - widely available)

## Decision 2: Greedy Selection vs. Optimization

**Choice**: Greedy algorithm (iteratively select best pair)

**Alternatives considered**:
1. Global optimization (linear programming, simulated annealing)
2. Graph matching algorithms (Hungarian, Blossom)
3. Machine learning predictor

### Why Greedy?

**Advantages**:
- **Fast**: O(m log n) vs. O(n³) for global optimization
- **Simple**: 100 lines of code vs. complex optimization frameworks
- **Interpretable**: Clear selection logic
- **Good enough**: 88-95% coverage (near-optimal in practice)

**Disadvantage**: Not globally optimal

**Why acceptable**:
- Chemistry is stochastic (100% bonding unrealistic)
- 90% coverage matches experiments
- Speed enables iteration (compensates for sub-optimality)

<Accordion title="Could We Do Better with Global Optimization?">
  **Theoretical analysis**: Global optimization algorithms (linear programming, simulated annealing) have O(n³) complexity

  **Tradeoff**:
  - Global optimization: Higher coverage (approaching 100%), much longer runtime
  - Greedy: High coverage (88-95%), fast runtime
  - **Marginal coverage improvement at significant time cost**

  **Conclusion**: Greedy's speed more valuable than perfect coverage for iterative design workflows
</Accordion>

## Decision 3: Python Implementation

**Choice**: Pure Python with NumPy/sklearn

**Alternatives considered**:
1. C++/Fortran for speed
2. Julia (scientific computing)
3. Cython (Python + C hybrid)

### Why Python?

<CardGroup cols={2}>
  <Card title="Accessibility">
    - **Familiar** to computational chemists
    - **Easy to modify** for custom applications
    - **Rich ecosystem** (NumPy, scikit-learn, MDAnalysis)
  </Card>

  <Card title="Development Speed">
    - **Rapid prototyping** (100× faster development than C++)
    - **Interactive debugging** (IPython, Jupyter)
    - **No compilation** (change code, run immediately)
  </Card>

  <Card title="Performance">
    - **NumPy** delegates to optimized C/Fortran (BLAS, LAPACK)
    - **sklearn KDTree** implemented in Cython (C-speed)
    - **Bottleneck**: KD-tree queries (already optimized)
  </Card>

  <Card title="Integration">
    - **MD packages** (MDAnalysis, PyMOL) are Python
    - **Workflow scripts** naturally Python
    - **No language boundaries**
  </Card>
</CardGroup>

**Performance analysis**:
- Bottleneck: KD-tree queries (already optimized in sklearn's Cython implementation)
- Most runtime spent in optimized C/Fortran libraries (NumPy, sklearn)
- Pure Python overhead minimal
- **Rewriting in C++ would provide marginal gains, not worth development cost**

## Decision 4: Stateful Objects vs. Functional

**Choice**: Object-oriented with mutable state (Atom.is_bonded_external, Chain.bonded_chains)

**Alternative**: Functional programming with immutable data

### Why Stateful?

**Scenario**: Accept pair, update affected atoms/chains

**Stateful (current)**:
```python
# Accept pair
pair.atom1.is_bonded_external = True
pair.atom2.is_bonded_external = True
chain1.add_bonded_chain(chain2.chain_id)
# State updated in-place, affects future calculations
```

**Functional (alternative)**:
```python
# Create new state
new_atoms = {
    **atoms,
    atom1.serial: Atom(..., is_bonded=True),
    atom2.serial: Atom(..., is_bonded=True)
}
new_chains = update_chain_connectivity(chains, chain1_id, chain2_id)
# Return new state, old state unchanged
```

**Stateful advantages**:
- **Memory efficient**: O(n) space vs. O(n×m) for copies
- **Natural**: Mirrors physical bonding process
- **Fast**: In-place updates vs. copying

**Functional advantages**:
- **Reproducible**: No hidden state
- **Parallelizable**: No shared mutable state

**Decision**: Stateful better for sequential greedy algorithm (no parallelization benefit)

## Decision 5: Lazy Deletion in Heap

**Choice**: Don't remove invalidated pairs from heap immediately

**Alternative**: Maintain heap invariant (remove invalidated pairs)

### Why Lazy?

**Scenario**: Accept pair A-B, invalidates pairs A-C, A-D, B-E, B-F

**Eager deletion**:
```python
# Find all pairs involving A or B in heap
affected_pairs = [p for p in heap if A in p or B in p]
# Remove from heap (O(n) operation × k affected pairs)
for pair in affected_pairs:
    heap.remove(pair)  # O(n) rebuild
```
**Cost**: O(kn) per accepted pair

**Lazy deletion** (current):
```python
# Do nothing when pair accepted
# When popped later, check validity:
if pair.atom1.is_bonded or pair.atom2.is_bonded:
    continue  # Skip, O(1)
```
**Cost**: O(1) per accepted pair

**Tradeoff**:
- **Pro**: Much faster (O(1) vs. O(kn))
- **Con**: Heap contains stale entries (wastes memory)

**Memory analysis**:
- Max heap size: ~10,000 pairs
- Memory: ~1 MB
- Negligible on modern systems

**Decision**: Lazy deletion faster, memory cost acceptable

## Decision 6: Two-Class Hierarchy (BondPredictor → PolymerizationPredictor)

**Choice**: Inheritance for radical-specific logic

**Alternative**: Single class with conditional logic

### Why Inheritance?

**Separation of concerns**:
- `BondPredictor`: General cross-linking (click chemistry)
- `PolymerizationPredictor`: Adds radical tracking (C-C bonds)

**Current**:
```python
class BondPredictor:
    def predict(self):
        # Generic prediction logic
        pass

class PolymerizationPredictor(BondPredictor):
    def predict(self):
        super().predict()
        self.find_radicals()  # Extra step
```

**Alternative (single class)**:
```python
class Predictor:
    def predict(self, mode='click'):
        # Generic prediction
        if mode == 'polymerization':
            self.find_radicals()  # Conditional
```

**Inheritance advantages**:
- **Extensible**: Easy to add new chemistries (DielsAlderPredictor, etc.)
- **Clear**: Each class has single responsibility
- **Testable**: Test each class independently

**Single-class advantages**:
- **Simpler**: Fewer files

**Decision**: Extensibility more important than simplicity (research code evolves)

## Decision 7: Text File I/O vs. Binary

**Choice**: Plain text outputs (pair_output.txt, radical_output.txt)

**Alternative**: Binary formats (HDF5, pickle, msgpack)

### Why Text?

**Advantages**:
- **Human-readable**: Inspect with `cat`, `less`, text editor
- **Tool-friendly**: Easy to parse with awk, grep, Python
- **Stable**: Format won't break with version changes
- **Debuggable**: See what algorithm produced immediately

**Disadvantages**:
- Larger file size (~2× vs. binary)
- Slower parsing (~10× vs. binary)

**Performance analysis**:
- Output file: ~10 KB (400 pairs × 25 bytes/line)
- File I/O time negligible compared to algorithm runtime
- **Text vs. binary makes no measurable difference** to end-to-end performance

**Decision**: Human-readability worth the tiny performance cost

## Decision 8: No Database / No Persistent Storage

**Choice**: Stateless execution (read PDB → write outputs → exit)

**Alternative**: Database to store predictions, track experiments

### Why Stateless?

**Current workflow**:
```bash
python3 predict.py input.pdb → output.txt
# No state persisted
```

**With database**:
```bash
python3 predict.py input.pdb
# Store in DB: structure, predictions, parameters, timestamp
```

**Stateless advantages**:
- **Simple**: No DB setup, migrations, maintenance
- **Reproducible**: Same input → same output (deterministic)
- **Portable**: Copy files, no DB to export/import

**Database advantages**:
- **Queryable**: Find all predictions with >90% coverage
- **Traceable**: Which parameters produced which results?

**Decision**: Simplicity prioritized

**Rationale**: LNKD is research tool (10s of runs), not production system (1000s of runs). File-based workflow sufficient.

**Future**: If usage scales, database wrapper could be added without changing core

## Decision 9: Single-Threaded Execution

**Choice**: No parallelization (runs on 1 CPU core)

**Alternative**: Multi-threaded KD-tree queries or pair evaluation

### Why Single-Threaded?

**Bottleneck analysis**:
- KD-tree queries: 30% of runtime (sklearn internals, hard to parallelize)
- Greedy selection: 50% of runtime (inherently sequential)
- Pair creation: 20% of runtime (potentially parallelizable)

**Parallelizing pair creation**:
```python
from multiprocessing import Pool

def create_pair(args):
    i, j, dist = args
    pair = Pair(atoms[i], atoms[j], dist)
    pair.probability = calculate_bond_potential(pair)
    return pair

with Pool(8) as pool:
    pairs = pool.map(create_pair, pair_indices)
```

**Expected speedup**: Limited by Amdahl's law (only 20% of runtime parallelizable)

**Cost**: Code complexity, debugging difficulty, cross-platform compatibility issues

**Decision**: Marginal speedup not worth added complexity

**Justification**: LNKD runtime negligible compared to MD simulation time (hours to days)

## Lessons Learned

<AccordionGroup>
  <Accordion title="Premature Optimization">
    **Initial plan**: Custom C++ KD-tree implementation for "maximum speed"

    **Reality**: sklearn's KDTree already highly optimized (Cython implementation)

    **Lesson**: Profile before optimizing. Python + well-chosen libraries often sufficient.
  </Accordion>

  <Accordion title="Simplicity Enables Science">
    **Observation**: Researchers modified LNKD for custom chemistries (Diels-Alder, disulfides)

    **Success factor**: Simple Python code easy to hack

    **Lesson**: Code clarity > micro-optimizations in research software
  </Accordion>

  <Accordion title="Text Outputs Aid Debugging">
    **Anecdote**: User reported "wrong predictions" for glycosidase system

    **Debug process**: `cat surface_pair_output.txt`, spotted atoms from same chain

    **Fix**: 10-minute fix after seeing plain-text pairs

    **Lesson**: Human-readable outputs save debugging time
  </Accordion>

  <Accordion title="Greedy is Good Enough">
    **Theoretical concern**: Greedy algorithm sub-optimal

    **Practical reality**: 90% coverage matches experimental efficiency

    **Validation**: Tested global optimization, marginal improvement

    **Lesson**: Don't over-engineer for theoretical perfection
  </Accordion>
</AccordionGroup>
